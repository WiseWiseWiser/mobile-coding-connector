机制要点（与实现对齐）

1. 清理逻辑只有一份：抽到 dot-pkgs，clear-tmp 与 ai-critic 共用

  • 事实：clear-tmp 在 github.com/xhd2015/my-private-working-note/projects/clear-tmp（私有仓库）， ai-critic（开源）不能 import 它；而把删除逻辑抄一份进 ai-critic 更不可接受——allowlist、iTerm 运行中跳过、 codex release 保留最新、sudo 闸门，都是真删文件的代码，两份实现必然漂移。
  • 因此把 clear-tmp 的核心清理层抽进公共库 dot-pkgs（已存在的模块 go-pkgs， 不新建 go.mod、不新建 tag namespace），两边都从同一个 import path 拿： github.com/xhd2015/dot-pkgs/go-pkgs/disk/reclaim。
  • 代码归属（约 2,700 行从 clear-tmp 搬走，clear-tmp 自己还剩 ~3,700 行 CLI/Web/podman/history）：
    包内容来源
    go-pkgs/disk/reclaimStep / Op / Tier / Registry / Plan / Selection / Run / Steps / Display / Elevate / Size / Human / Historysteps.go、run.go、plan.go、selection.go、size.go、human.go、dirs_cleaner.go 的 elevate 片段
    实际落成一个扁平包（measure/elevate/human/steps 没有再拆子包）： 拆开只会多四层 import 噪音，而这里每一层都只被 reclaim 自己用； 对外只暴露 StepInfos(home)（纯数据 + Actions []Op）和 ScanSteps(opts, ids)（按 id 子集测量）， 宿主 UI 不需要 Run 的内部结构。
  • 发布顺序：一个 tag go-pkgs/v0.0.204（覆盖 go-pkgs/disk/...； 203 是第一次抽取，204 补了 StepInfos/ScanSteps 与 go-mod-cache 清单行）→ clear-tmp 改 require ... v0.0.204 并删掉搬走的文件（--dry-run --json 只允许多出 display 字段， diff 为空才算抽对）→ ai-critic 把 go-pkgs v0.0.203 → v0.0.204。 CI 不用改：.github/workflows/test.yml 里的 go -C go-pkgs test -v ./... 天然覆盖 go-pkgs/disk/...。
  • 代价（明确的）：clear-tmp 的 go.sum 会多出 go-pkgs 的 ~30 个间接依赖（只在 module graph，二进制体积不变）； ai-critic 已有 go-pkgs v0.0.200，只改版本号一行。
  • 被否掉的方案：调已安装的 clear-tmp 二进制（运行时依赖、每次 dry-run 实测 60s+、错误不可观测）； separate repo dot-pkgs-disk（多一套 tag/CI）；在 ai-critic 里重写一份（必漂移）。

2. 分类与清理类分开，互不污染

  • 空间桶（xcode/containers/dev-cache/caches/media/downloads/logs/other）继续只负责图表与趋势， 不变的不变量：sum(bucket.bytes) == walked_bytes、bucket id 稳定（趋势曲线按 id 连）。
  • 清理类是动作，id 直接来自公共库的 registry（sandbox-gocache…，不在 ai-critic 里手写第二份列表）、带 tier、op 列表、可执行性。 它们不参与饼图，只在自己的分区里逐行列出——所以「新增 Go build cache / Go mod cache」不会把曲线打断。
  • 两者的桥：清理类带 bucket 字段（从同一个前缀表推得），报告页点清理类可以跳到对应的空间桶趋势；reclaimable 改为 「可清理类的实测总和」，不再用路径前缀猜。

3. 尺寸从哪来（不重扫整台机器）

  • 不复用扫描报告：报告是按 bucket 折叠的，清理类的根目录和 bucket 前缀不是一一对应，从报告里抠数字会算错。 改为清理面板自己测：reclaim.ScanSteps(opts, ids) 只走这 21 条路径。
  • GET /cleanup/plan 永不阻塞：第一次调用立刻返回骨架（measured:false, pending:true）， 同时后台跑一遍 ScanSteps；前端每 1.5s 轮询，pending 消失后数字逐行落定。实测整轮 ~50s（go-build-cache 9.9 GB 占大头）。
  • system tier 的 3 条不进后台那一轮：ios-sim-runtimes 会 shell out xcrun simctl、dirs-cleaner 要 sudo， 放进去会让整个 plan 卡住甚至挂死。它们只在用户展开 system tier 时走 POST /cleanup/measure，60s 超时就返回 {"pending":true} 让前端继续轮询。
  • 测不出来就显示 — / not sized（ios-sim-mobileasset、dirs-cleaner 今天就是）， 不瞎填数字；measured:false 的行不计入 totals，所以「可清理 X GB」永远是已测之和。

4. 接口（与实现一致）

  • GET /api/server/disk/cleanup/plan（?refresh=1 强制重测）→ {home, scannedAt, scanMillis, pending?, volume?, groups[], classes[], totals{selectedBytes, aggressiveBytes, systemBytes, inventoryBytes, unmeasured}}。 每个 class 带 id, group, label, sizeBytes, measured, selected, readOnly, actions[], command, paths[], notes[], details[]—— actions[] 由公共库从 op 列表渲染，前端只负责显示，绝不拼命令。
  • POST /api/server/disk/cleanup/measure {ids:[]} → {"pending":bool}；只给 system tier 用。
  • POST /api/server/disk/cleanup/run {ids:[], sudo:"ask"|"never"} → SSE：meta（home/steps/sudo/sudoGranted）/ section / progress（每 step 一条 status: running|skipped|done + detail + freedBytes）/ log（工具原样输出）/ done（{freedBytes, results[], skipped[]}）。 sudo:"never" 时 admin 类直接进 skipped[]（reason needs administrator authorization）并附可复制命令， 后台永不弹框。
  • 并发：清理在跑时再 POST 回 409 a cleanup is already running；清理结束会 invalidate() 掉缓存的尺寸，下次 /plan 重新测。 没有 cancel 接口——每个 step 都很短，关掉 SSE 连接即放弃后续 step。
  • 不写清理历史：~/.ai-critic/disk/<id>.json 只存扫描报告，清理结果随 SSE 一次性返回，不落盘（避免 schema 又要加字段）。

5. 安全线（会被测试逐条钉住）

  • 只接受注册表里的 step id，请求体里的任意路径一律丢弃（不提供「删这个路径」的通用接口）。
  • 没有 confirm 字段：selected 非空就是确认，ids 为空回 400。aggressive 与 system 必须在 UI 上显式勾选。
  • 路径只可能落在 {Home}、/Applications、/private/var/dirs_cleaner、/System/Library/AssetsV2 四处白名单内（与 clear-tmp 相同）。
  • go-mod-cache 以 readOnly:true 的 inventory 行出现（显示 go clean -modcache 是因为它是清单项）， 但 resolveRun/measureClass 都拒绝它：POST /run 带它回 400，POST /measure 同样拒绝。 命令永不被执行，公共库侧另有 steps.go:173 的硬性 prohibit + aggressive_steps_test.go 断言。
  • 外部命令按 step 白名单执行（brew/npm/pnpm/go/xcrun/sudo），exec.Command(argv[0], argv[1:]...)，任何路径都不拼进 shell； rm -rf 只是显示形态，执行走 os.RemoveAll + 白名单校验。
  • root 操作只能通过 elevate 包的四级链，禁止在别处直接调 sudo；密码只在第 3 级 /dev/tty 里读，且不落任何结构体字段。

6. 显示即行为：rm -rf 还是官方命令，由 op 列表算出来

  • step 定义不再只有 Apply func()，而是结构化 op 列表： Op{Kind: remove|remove-glob|exec|script, Paths, Argv, Script, SkipRunning, KeepNewest}。 执行按 kind 分派，显示也从同一份 op 渲染（Step.Display(home) []string）， 所以「UI 上写的命令」和「真的跑的东西」在类型层面就绑死，不可能漂移。
  • 展示规则（用户要求的就是这条）：等价 rm -rf 的删除 → 显示 rm -rf ~/.sandbox/gocache （执行走进程内 os.RemoveAll，不经过 sh -c）；官方工具 → 原样显示 go clean -cache / brew cleanup -s --prune=all / pnpm store prune / xcrun simctl runtime delete all； 混合型 → 按顺序多行（brew-cleanup 就是「官方命令 + rm -rf ~/Library/Caches/Homebrew」两行）； 需要 root → 前面标 sudo。
  • 有 3 个 step 的测量路径 ≠ 命令路径（codex releases 只删旧版、iTerm 跳过运行中、pnpm store 由工具自己决定删什么）， 这些行额外给一句 measured: … 说明，避免「命令和数字对不上」的困惑。
  • --dry-run --json 在保留旧 command 字段的同时新增 display[]； clear-tmp 的 web UI 继续用旧字段，ai-critic 用新字段——同一份数据，两个消费者。

7. 需要 root 的 step（用户要求：弹密码框，而不是直接说 no）

  • 受影响的只有 3 个：dirs-cleaner（sudo find /private/var/dirs_cleaner -mindepth 1 -maxdepth 1 -exec rm -rf {} +）、 ios-sim-mobileasset（sudo chflags + rm -rf）、ios-sim-runtimes（xcrun simctl runtime delete all）。
  • 四级链（reclaim 里的 elevate 部分）： ① sudo -n true 静默探测，已有 ticket 就直接跑（重复清理不重复弹框）； ② osascript -e 'do shell script "…" with administrator privileges' 弹 macOS 原生密码框 （脚本走 base64 传参，避开引号地狱；仅当 launchctl managername 为 Aqua 才尝试，SSH 会话下跳过）； ③ 落在启动服务那个终端的 /dev/tty 上 sudo -S 读密码（今天的服务就是从终端起的，日志写 ~/ai-critic-server*.log）； ④ 60s 无人输入 / 全部失败 → 该 step 记 skipped: needs admin + 一条可复制的完整命令，不影响其他 step。
  • 密码永不跨 HTTP：不进请求体、不进服务端内存里的可序列化结构、不进日志、不进 服务端日志、不进 SSE 帧。 Web UI 里没有密码输入框——远程打开页面只会看到那条 class 停在 running，失败后变成 skipped: needs administrator authorization。
  • 开关：--sudo=auto|ask|never（默认 auto），--sudo-forget 用完即 sudo -k。 never 时这 3 个 step 直接标 needs-admin，UI 上按钮变灰 + 复制命令。
  • 测试：elevate 用一个假的 Runner 注入，断言「sudo -n 成功就不再弹框」「osascript 失败后落到 tty」「全都失败只返回 ErrNeedsAdmin 而不返回密码相关内容」； 密码字符串在测试里用一个哨兵值，断言它不出现在任何返回结构/日志里。
