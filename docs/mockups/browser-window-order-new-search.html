ai-critic /browser · design mockup

Windows by creation time,
a NEW badge per window and tab, and tab search.

Three additions to the phone sheet and the desktop rail, drawn against the shipped surfaces (402 pt sheet, 56 / 189 pt rail, 288 pt desktop rail). Oldest window first; NEW marks what you have not opened yet; search filters every live window's tabs by title or URL. Everything below is client-side — no extension version bump, no new server contract.

Desktop rail

Same three contracts in the 288 pt rail: rows sorted by creation, a NEW pill on the session line and on its tabs, and an always-visible search field with ⌘K.

Creation order

Chrome exposes no timestamps. Window ids are monotonic within a browser run (the extension already sorts by them), so the client sorts rows by window_id ascending and keeps two sessions of one window adjacent by session id. Rows without a window id (a disconnected registry entry) sink to the bottom. The rail keeps printing the session id — the window id is only the sort key.

Known limit, stated on purpose: after a Chrome restart, restored windows take new ids and therefore restore order, not their original birth order. No extension change is needed to fix that, so this design does not.

NEW · windows

Unread = not clicked yet. A window that shows up after this client's first poll earns a pill; tapping the row — preview or switch — clears it. Merely rendering the row does not: a badge is a call to look, not a display artifact.

State lives in localStorage per client (like the rail's open state), pruned to live ids on every poll — that also stops a recycled id from silencing a genuinely new window. The very first run seeds what is already open as read, so day one is quiet.

NEW · tabs

A tab id absent from the read set is new, whether the window is old or new. It clears when the tab is followed (tapped in the pane, or opened from a search result) — not when the window is previewed, and not when the list is rendered.

Consequence worth keeping: you can open a brand-new window and still see which of its six tabs you have actually read.

Search

Case-insensitive substring over tab title and URL, computed from the sessions payload already in memory — instant, offline, no endpoint. Matches are highlighted in both lines.

It is a row, not a view: the field sits permanently under the header (desktop: under the rail head), and typing swaps the body below it for the result list. Same height, same scroll position, no overlay, no back button — clear the query and the window list returns where it was.

The /go?session= control page is excluded by role; a window with no tabs (disconnected) contributes nothing. Grouping follows window creation order, rows follow tab order, and there is no relevance shuffle — the list never reorders under the finger.

Assumptions. English UI, “NEW” is the literal pill text (uppercase, 7.5 pt mono, accent tint). Phone gets a permanent search row and renders results in the existing list area (no overlay, no extra sheet height); desktop gets the same row plus ⌘K. Read state is per device, not synced — if the same “checked” should hold on phone and desktop, that is the one decision that would require a small server ledger (POST /api/browser/windows/seen) instead of localStorage.
